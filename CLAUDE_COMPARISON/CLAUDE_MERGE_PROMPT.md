# Claude Code 任务：独立审阅两个版本，融合形成最终论文

## 目标与目录

本 GitHub 仓库包含同一篇 IEEE 英文论文的两个版本，通常位于 `CLAUDE_COMPARISON/` 下；若目录直接放在仓库根目录，则以实际位置为准：

- `01_original/`：由 Claude Code 生成的原始版本。主源码为 `main.tex`，原稿 PDF 为 `main_preview.pdf`，并附 MATLAB 源码、原始结果和图。
- `02_revised/`：在原版本基础上经 GPT/Codex 修改的版本。主源码为 `main.tex`，PDF 为 `main_revised.pdf`，并附更新后的 MATLAB 源码、保存的结果和九张论文图。
- `03_review_notes/`：如存在，包含源码差异、文件对应索引、历史修改规范及验收证据。它是辅助材料，不代表独立学术结论。

请以独立 IEEE Transactions 审稿专家兼通信优化研究者的身份，先分别审阅两版论文，再综合两者有证据支持的优点，直接生成逻辑严密、表达自然、代码与论文一致的最终版本。不要预设某个模型或较新的版本一定正确。可保留任一版的内容，也可提出更准确的第三种写法；不要机械拼接或平均折中。

保留 `01_original/` 和 `02_revised/` 作为固定比较基准，在同级新建 `04_final/` 实施融合。若旧提示词要求只读对比，本次授权在 `04_final/` 创建和修改最终论文及必要代码，原有两个基准目录继续保留。

## 执行顺序

### 1. 分别审阅，形成独立判断

各完整通读一次两版 `main.tex`，分别判断其问题、成立的贡献和可保留的优点；这一轮先依据论文与必要源码形成结论，再查阅历史审稿意见，减少结论锚定。随后使用 `03_review_notes/FILE_COMPARISON_GUIDE.md`、`main.tex.diff`、`MATLAB_AND_README.diff` 定位分歧，只回看相关上下文。

优先检查：

1. 系统物理假设、优化变量、约束、目标与评价指标是否闭环；P1 原始策略、P2 的 ZF/零空间 AN 限制及 P3 确定性近似是否明确区分。
2. 数学推导与算法是否成立：等价变换和近似的区别、维度与归一化、约束可行性、固定条件下的功率解、有限网格搜索、位置更新、伪代码和复杂度。区分目标值收敛、迭代点收敛、驻点与全局最优。
3. 摘要、引言贡献、推导和实验结论是否互相支持。摘要应交代物理矛盾、优化建模、求解难点、针对难点的转化与求解逻辑，以及证据支持的性能结论。
4. IEEE 写作是否准确、凝练、连贯，符号和引用是否统一。保留必要的保证边界，同时压缩重复的限制说明和无信息量表述，避免夸大或无依据地削弱贡献。
5. 仿真是否检验理论与物理机制，代码、参数、图和文字数字是否一致。数据按 scheme 名称对齐，勿仅按列序比较；严格保持文中“先对两类速率取期望，再取差的正部”的 ESSR 定义。

历史 PASS、编译成功和大量测试均不能替代数学正确性论证。只有源码、数据、推导或实际执行支持的发现才可确认为问题；其余标为待验证。

### 2. 作出取舍并落实融合

在 `04_final/MERGE_DECISIONS.md` 用简短表格记录实质分歧：问题位置、两版各自的优缺点、最终选择及关键依据。常规语言调整合并说明，不逐句复述。不能仅凭“更严谨”“更专业”决定取舍，应给出足以核验的具体理由。

可从较便于整理的一版复制必要文件建立工作目录，但最终内容由独立判断决定。完成全文和必要代码的实际修改，不停留在审稿意见或修改计划。发现两版共有的问题，也应修复。保留有效的 `\label{}`、引用键和已成立的结果；不得编造作者信息、参考文献、实验数据或数学保证。作者及单位占位为已知待补充项，不构造虚假信息。

### 3. 验证并交付

先做静态推导核查、现有数组检查和针对性的最小数值验证。若算法或参数修改会影响输出，实际重跑受影响实验，更新对应图及全文相关数值；若仅改文字且数据链不变，可复用有明确来源的结果。不要为了表示工作量而默认重跑全部耗时仿真。

按项目实际方式完成至少两次 LaTeX 编译，修复未定义引用、重复标签、公式越栏等问题；检查最终双栏 PDF 中的公式、算法、图表、标题和页面边界。不能通过缩小全局字体、缩减页边距或屏蔽警告掩盖排版错误。无法执行的验证必须明确记录，不以缓存、历史报告或启动进程代替本次完成证据。

在 `04_final/` 交付：

- `main.tex`、`main_final.pdf`，及编译和复核所需的图、必要代码与结果；使用正确的相对路径，不混入过期 PDF 或无关缓存。
- `MERGE_DECISIONS.md`：重要取舍及依据。
- `VALIDATION.md`：实际执行的验证、数据来源、结果及未解决事项。
- `README.md`：最终入口、编译方式和仍需用户补充的信息。

## Token 与进度规则

- 主文两版各完整读一次；之后按差异和未决问题定点读取，避免反复吞入整篇论文或整库文件。
- 不递归读取运行缓存、二进制文件、全部日志或参考 PDF。MAT 按需用程序提取小型数值摘要；图表按需查看，不把二进制内容塞入上下文。
- 用一个紧凑的问题/决策表持续记录已闭环事项。遇到新证据再重开，不重复分析已有定论；进度更新只说新发现、当前阻点和下一步。
- 不因为追求节省 token 而省略必要证明或验证。优先解决影响结论的错误，再处理全文表达与排版；避免无依据扩大任务范围。
- 接近上下文或额度上限时，先保存修改及 `04_final/RESUME.md`，记录完成项、未决项、证据位置和下一步最短执行指令。下一次先读该记录续接，避免从头审阅。

请自主执行到可交付的最终版本。最终回复只简述产物路径、关键融合选择、验证状态和真正需要用户处理的事项。
